# The record adapter

**`models.py` is the source of truth for the schema.** Declarative, not
SQLAlchemy Core — measured, not a preference: `ty` resolves `Eval.scor_mbb` to
an attribute error and does **not** catch `evals.c.scor_mbb`, because Core's
`.c` is a dynamic `ColumnCollection`. Core would cost a dependency and buy none
of the safety that usually justifies it.

Storage models, deliberately not payload models. The console's contract is
generated from its own pydantic models, and fusing the two would make a column
rename a console change.

## Queries

Models for row shape and single-table access — every column reference there is
checked. `text()` SQL for anything with a **join, an aggregate or a window**,
beside the reader that owns it. The paired-within-seed comparison *is* a join,
and a builder obscures the thing that makes it a pairing.

That is two ways to write a query, which is a real cost. The line is narrow and
checkable, and if it starts getting argued about it was the wrong line.

## Migrations

Alembic, against `POKER_SOLVER_RECORD_DSN` from the environment — never from
`alembic.ini`, because the DSN carries a password and that file is in the repo.

```
export POKER_SOLVER_RECORD_DSN=$(terraform -chdir=infra/store output -raw postgres_dsn)
uv run alembic upgrade head     # apply
uv run alembic check            # does the live DB match models.py?
```

**Autogenerated revisions are read, not trusted.** A dispatch seals its code
snapshot and runs 24–36 h, so a node is routinely writing week-old code against
this schema: every migration must be **additive while anything is in flight** —
new columns nullable, nothing renamed, no type narrowed. Autogenerate will
happily emit a `DROP` for a model attribute you deleted. Read the diff.

`alembic check` is the drift guard, and it is why the schema lives in Python
rather than in hand-written `.sql`: with DDL files there is no artifact that
says what the schema *is*, and nothing that compares it to the database.
